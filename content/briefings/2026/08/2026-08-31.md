Intel 在 Hot Chips 2026 公布了面向 Agent 工作负载的三层硬件体系：**Diamond Rapids Xeon + Crescent Island GPU + Wildcat Lake SoC**，分别覆盖数据中心编排、大规模推理以及客户端/边缘 Agent。Diamond Rapids 最高 256 核、1.28 GB LLC、16 通道内存；Crescent Island 则是一张 350W PCIe 推理卡，最高支持 480 GB LPDDR5X。[Newsroom](https://newsroom.intel.com/client-computing/intel-outlines-architectures-for-agentic-ai-at-hot-chips-2026?utm_source=chatgpt.com) · [Intel Hot Chips coverage](https://www.storagereview.com/news/intel-hot-chips-2026-256-core-diamond-rapids-crescent-island-with-480gb-for-inference-and-wildcat-lake-at-the-edge)

**为什么重要：** “Agentic AI”第一次越来越明显地影响处理器本身的设计目标。Agent 会制造大量并发工具调用、长上下文推理和持续推理负载，所以硬件竞争开始从单纯的训练 FLOPS 转向 **token throughput、内存容量、功耗与并发 Agent 数量**。

**实践 / 研究启示：** 以后评估 Agent 系统，不能只记录“用了哪个模型”。更有意义的指标会包括 **tokens/s、任务完成时间、显存/内存占用、并发 Agent 数和每任务成本**；Agent benchmark 很可能最终与硬件 benchmark 深度结合。

8 月 30 日报道的一项新研究测试了包括 Codex 和 Claude Code 在内的 Coding Agent，发现它们不仅难以预测一个任务需要多长时间，甚至不能可靠判断**自己已经工作了多久**。研究尤其指出，Agent 会系统性高估任务执行时间，而随着 Agent 运行时间变长，对已耗时间的估计误差也会积累。[The Decoder](https://the-decoder.com/ai-agents-have-no-sense-of-time-and-are-not-aware-of-it/?utm_source=chatgpt.com)

这个问题表面看很小，但对 persistent Agent 非常关键。一个运行几分钟的聊天模型不需要准确感知时间；一个持续运行数小时乃至数天、管理多个子任务的 Agent，却必须知道 deadline、timeout、任务预算以及何时应该重新规划。

**为什么重要：** Agent 要真正实现：

`Plan → Work → Monitor → Replan → Continue`

就必须拥有可靠的外部时钟与状态，而不能依赖 LLM 自己“感觉过了多久”。

**实践 / 研究启示：** 构建长任务 Agent 时，**时间应该作为环境状态显式注入**。例如 Harness 直接向模型提供 `current_time`、`task_start_time`、`elapsed_time`、`deadline` 与剩余 compute/token budget，而不是要求模型自己推测。

这类看起来“不 AI”的 Harness Engineering，反而很可能决定 Agent 最终是否可靠。

随着 Agent 开始自主调用 API、数据库和企业系统，8 月 30 日的一篇产业分析提出了一个越来越重要的观点：**Agent 不应该继续借用人类用户的身份和凭证，而应该拥有自己的机器身份。** 换句话说，企业需要知道的不只是“哪个用户启动了 Agent”，还包括“到底是哪一个 Agent、哪个版本、以什么权限执行了这个操作”。[Venturebeat](https://venturebeat.com/security/ai-agents-need-their-own-identity-before-they-need-a-gateway?utm_source=chatgpt.com)

**为什么重要：** 软件时代的安全基本单位是：

\[
\text{User} + \text{Application}
\]

Agent 时代可能变成：

\[
\text{User}
\rightarrow
\text{Agent}
\rightarrow
\text{Sub-Agent}
\rightarrow
\text{Tool/API}
\]

每一层都需要独立的权限、审计和撤销机制。

**实践 / 研究启示：** 做 Coding / 游戏开发 Agent 时，可以从现在就把 **Agent Identity、最小权限、短期凭证、操作日志、sandbox 和 human approval** 纳入 Harness，而不是让 Agent 直接继承开发者全部系统权限。

虽然论文发表于 8 月 10 日，但过去 24 小时再次受到关注，因此今天值得破例纳入。Pathway 的 **BDH-CQ: In-Context Learning with Recurrent Latent Reasoning** 使用只有 **150M 参数**的模型，在 ARC-AGI-1 达到 29.5% pass@2，而计算出的单任务推理成本只有 **$0.0007**；其核心不是生成越来越长的 Chain-of-Thought，而是在高维 latent state 中循环执行推理。[Papers with Code](https://paperswithcode.co/paper/2608.09888?utm_source=chatgpt.com) · [BDH-CQ arXiv paper](https://arxiv.org/abs/2608.09888)

作为参照，Pathway 报告 GPT-5.6 Luna Low 在相同 benchmark 上为 34.2%，但对应成本约高 **11 倍**。需要注意，这是一个非常特定的 ARC-AGI-1 成本—准确率比较，并不能据此认为 150M 模型整体能力已经接近 frontier LLM。[路径](https://pathway.com/research/introducing-bdh-cq?utm_source=chatgpt.com)

**为什么重要：** 当前 reasoning model 的主流范式实际上是：

\[
\text{更多推理}
\approx
\text{生成更多 reasoning tokens}
\]

BDH-CQ 提出的则是：

\[
\text{更多推理}
\approx
\text{latent space 中执行更多 recurrent computation}
\]

如果后者能够扩展到语言、Coding 和 Agent 任务，它可能显著降低长时间 Agent 的 token 成本。

**研究启示：** 这篇论文最值得关注的不是 29.5% 这个数字，而是 **Recurrent Latent Reasoning**。对于长期运行 Agent，“思考”未必永远需要转化成数千甚至数万 token；未来可能出现内部 latent computation 很长、真正输出 token 很少的 Agent。
